# 三种场景的操作细则

先判断用户要做什么，再照对应流程走。判断依据是**用户想要的结果**，不是他的措辞。

## 场景判断

| 用户想要 | 场景 | 典型说法 |
|---|---|---|
| 一条或几条新脚注 | L1 | 「这段引了……帮我加个注」「这句话的出处怎么写」 |
| 知道现有脚注哪里不对 | L2 | 「帮我核一下」「这些脚注规不规范」「老师说要按手册改，先看看有哪些问题」 |
| 拿到改好的文件 | L3 | 「直接帮我改好」「按规范重排一遍给我」 |

判断不了就问一句：「你是想让我核一下问题，还是直接改成规范版？」

---

## L1：单条生成

### 步骤

1. **提取字段。** 从用户给的材料里找：作者、著作方式、文献名称、版次、译者、
   出版社、年份、页码/章节、网址、访问日期等。

   材料可能是：一段文字、一张版权页截图、一个网址、一句口述。截图要读图，
   网址要打开看页面。

2. **定类型。** 拿不准就查表：`run.py types`。常见的几种：

   | 材料 | 类型 |
   |---|---|
   | 有出版社和年份的图书 | `book` |
   | 「载《期刊名》xxxx年第x期」 | `journal` |
   | 「载《报纸名》xxxx年x月x日，第x版」 | `newspaper` |
   | 「载某人主编：《论文集名》」 | `collection` |
   | 「xxxx年x（博/硕）士学位论文」 | `thesis` |
   | 「xx法院(xxxx)……号判决书」 | `case` |
   | 「《法名》第x条」 | `legal` |
   | 带网址的网页文章 | `online` |
   | 「载微信公众号"xx"」 | `wechat` |

3. **看字段说明。** `run.py show --type <类型>` 会列出字段、依据条款和示例。
   字段名不要凭印象写。

4. **生成。**

```bash
python scripts/run.py cite --type book --file data.json
```

### 信息不全怎么办

不要猜，也不要因为缺字段就不做。正确做法是先产出能确定的部分，再明确列出缺口：

> 按你说的作者和书名，先出这一条：
> 张新宝:《侵权责任法》,中国人民大学出版社2020年版。
> 还缺两个信息才能定稿：**版次**（是第几版）和**你引用的页码**。

页码/章节缺失时手册允许不标（第 48 条），但版次和年份影响辨识，要问。

## L2：整篇核查

### 步骤

```bash
python scripts/run.py doc-check --file 论文.docx --out 核查报告.md
```

### 报告怎么读

四条统计线：

- **完全合规**：引擎能逐字复现。这些不用管。
- **标点需规范化**：字段和式样都对，只是用了全角标点。手册印刷示例用半角
  冒号与逗号，所以这类算需要规范化，可以一键处理。
- **格式不符**：字段对、式样不对。报告会给出「建议改为」和具体差异点
  （哪几个字多余、少了什么）。
- **未能解析**：模式没认出。**这不是你写错了**，而是这种写法超出了规则解析
  范围（常见于法、德、意、俄、日文献）。需要补字段。

### 汇报给用户

不要甩报告原文。按这个顺序讲：

1. 一共几条脚注，几条没问题；
2. 有问题的是哪几条，每条一句话说明问题；
3. 问他要不要直接改（进入 L3）。

示例：

> 这篇论文共 23 条脚注，18 条规范。有 3 条是全角标点（第 2、9、14 条），
> 2 条式样不对：第 7 条案号里的年份缺了括号，第 19 条期刊论文漏了「载」字。
> 另有 2 条我认不出来（第 5、16 条是德文文献），需要你确认一下作者和书名。
> 要我把前 5 条直接改好另存一份吗？

## L3：批量改写

### 前置确认（不可跳过）

执行前必须让用户知道：

1. 输出是**新文件**，原件不动，随时可以对照；
2. 只会改「标点需规范化」和「格式不符」两类；
3. 「未能解析」的**不会被改**，这就是为什么要先问清它们的字段。

### 步骤

```bash
python scripts/run.py doc-rewrite --file 论文.docx --out 论文_已规范.docx --table 变更对照.md
```

### 改完要报告

- 改了哪几条（位置 / 改前 / 改后）；
- 哪几条没改、为什么；
- **写回复核结果**：引擎写完后会重新读一遍输出文件确认改动落地，报告里会写
  「写回复核：通过」或列出不一致的地方。这一项要如实转达。

如果写回复核未通过，**不要**把文件当成功交付，先把不一致的地方给用户看。

## 附：手工兜底

引擎认不出的脚注，可以让用户确认字段后用 `cite` 单独生成，再手工填回文档。
不要把「引擎认不出」当成「无法处理」告诉用户。

若用户手上有某刊物的特殊式样，可用 `--rules <目录>` 指定改过的规则目录，
不必改代码。
